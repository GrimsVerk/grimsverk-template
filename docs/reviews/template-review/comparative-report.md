**Repos compared:**
- Testbed: `grimsverk/testingbed` @ `claude/agent-design-doc-template-lnr7jl` (15 files; I authored it this session from the short brief). Note: the branch in the task description, `…-1nr7jl`, does not exist on origin; `…-lnr7jl` (letter L) is the only branch and is what I used.
- Template: `grimsverk/grimsverk-template` @ `claude/copier-template-automation-rii78u`, commit `21c8eae` ("docs: the plan is implemented; what remains is observation").

**Bias disclosure and method.** I authored the testbed, so the default failure mode of this report is favoring familiar mechanisms and grading my own speculative guardrails as if they were proven. **Caveats on certainty.** I read the template's docs, AGENTS/DESIGN/VISION/oracle/escapes/acceptance files, copier.yml, and CLAUDE/GLOSSARY directly; the ~30 scripts, 7 commands, workflows, and test suite were read exhaustively by three sub-readers whose line-cited summaries I rely on for mechanics. The template itself flags five behaviors as unverified-live (`docs/automation-loop-plan.md:9-15,100`); I inherit that uncertainty wherever those behaviors matter.

## 1. Blind reconstruction (written before comparing)

*Read: the template repo only. This section reconstructs the template from its artifacts, as a test of its legibility as a spec.*

### What problem it appears to be solving

A [Copier](https://copier.readthedocs.io) template that **generates** project repositories (`README.md:3-5`, `copier.yml:5`); nothing in it ships directly. Each generated repo is a machine for one person — "the owner", default `@GrimsVerk` (`copier.yml:94-97`) — to turn an idea into working software with agents doing essentially all implementation, while the owner's authority over *intent* is preserved by mechanical gates rather than by supervision. The distinguishing obsession, visible everywhere in the artifacts, is **unattended operation**: what stops work while the human is asleep, and how each stop can be removed *without* transferring authority over the design to the agents. The owner's stated jobs are three: "approve the vision and design, review the result, loop" (`docs/plans/unattended-operation.md:19-21`); the diagnosed blocker is "not agent capability… it is that every pull request waits for a human hand" (`:21-22`).

### The workflow it assumes

idea → `/design` interview writes `docs/DESIGN.md` (requirements `R<n>`, success criteria `S<n>`) and `docs/VISION.md` (ordered priorities, tradeaways, core tenets) — agent-**written** but owner-**landed**: `.github/scripts/owner-authored.sh` fails any PR touching either file that the owner did not open → `/plan` writes `docs/plans/<slug>.md` (3-5 vertical slices, files, signatures, line estimates, an uncertainty gate with HIGH/LOW risk classes), which must merge **before** the code it plans → `/orchestrate` builds one feature: per slice, a coder and a **blind test-writer** in parallel worktrees, neither able to see the other's work, meeting at assembly; one PR → required checks (`checks`/`test`, `secrets`, `plan`, `template-sync`, `test-the-tests`, `review` — an LLM gate that fails closed) → **GitHub native auto-merge on green**; "the pipeline merges, not you and not the owner" (`template/AGENTS.md.jinja:10-11`) → an acceptance pass fills `docs/acceptance.md` per `S`-id, split honestly between `agent`-verifiable and `owner`-only rows.

When reality contradicts the design mid-run and nobody is awake, an **oracle** appends evidence-cited decisions (`OD-<n>`, citing only landed `ESC-<n>`/`BL-<n>` ids, quoting the `VISION.md` sentence relied on, requirement ids offset to R1000+) to a second, deliberately un-owned design document, `docs/DESIGN.oracle.md`, constrained by `.github/scripts/oracle-decisions.sh` rather than by a human. Unattended runs are driven by a deterministic scheduler (`deliver-loop.sh` locally or `/deliver-loop` in a web session, sharing one phase detector) with hard budget stops (iterations, PRs, wall-clock, subscription percentage points) and typed exit codes. Every defect that reaches the owner must produce a permanent check — the "ratchet" — logged append-only in `docs/escapes.md`.

### What it expects of the human

Steady state: land the vision and design (authorship, not just approval), optionally steer mid-run by editing those two documents, review and accept at the end. Around that: a substantial one-time setup ceremony (GitHub Pro or a public repo; SSH alias + `insteadOf` rule; `TEMPLATE_TOKEN` and optional `AUTO_MERGE_TOKEN`/App credentials; `claude setup-token`; ruleset configuration; a throwaway PR to register checks — `README.md:12-401`), the recurring CODEOWNERS self-approval deadlock whenever gate paths change (`README.md:383-400`), and token-expiry maintenance. The owner is also assumed to be *learning the vocabulary*: `GLOSSARY.md` carries communication rules and two word lists (learning vs. learned) that agents must respect.

### Legibility verdict

The template is unusually legible as a spec. Nearly every mechanism carries its rationale and often the incident that produced it in place (the 22-stale-branches story, `README.md:305-311`; the R2a id-grammar rejection, `template/docs/DESIGN.md.jinja:44-49`; the deliberately-not-relitigable escape-ordering ruling, `template/AGENTS.md.jinja:403-418`). Reconstructing intent required no guessing; the only uncertainty left after reading is runtime behavior the repo itself flags as unobserved.

## 2. What the testbed does better

Method: for each mechanism present in the testbed and absent (as such) from the template — (a) the failure it prevents, (b) whether the template prevents the same failure by other means, (c) verdict. Mechanisms where the search turned up a full equivalent are reported too, per the brief, since "absent from the template" turned out to be wrong more often than right.

### 2.1 Frozen executable acceptance suite (`acceptance/`, testingbed `acceptance/README.md`)

- **Failure prevented:** the agent grading its own homework — "done" claimed against tests the agent wrote or reinterpreted; and *regression of the definition of done* — a criterion that passed once silently breaking under later merges, because the check that proved it keeps running in CI forever.
- **Template equivalent, searched:** three partial mechanisms. Per-slice: blind test authorship (structural isolation in worktrees, `template/.claude/agents/test-writer.md.jinja:11-16`), `test-the-tests` (revert the implementation, keep the tests, fail if the suite still passes — `template/.github/scripts/test-the-tests.sh:12-16`), and `blind-tests.sh` (reports any post-blind edit to the reviewer). End-to-end: `docs/acceptance.md` — one evidence row per `S`-id, with an honest `agent`/`owner` verified-by split (`template/docs/acceptance.md.jinja:19-28`).
- **Verdict: genuine partial advantage, on the second half only.** The self-graded-homework failure is prevented by the template, arguably more cheaply (no human touchpoint per revision, where the testbed requires the human to approve acceptance-test changes each design revision). But the template's acceptance evidence is a *ledger of one observation* — a command run once during the acceptance pass — not a continuously-executing suite. A criterion that passed in the acceptance pass and regressed in a later merge is caught by nothing until the next acceptance pass. The testbed's `acceptance/` suite, running as a required check on every PR, prevents that continuously. The template's own epistemics ("a check must be observed working, not inferred" — six independent statements, e.g. `docs/escapes.md:26-32`) actually argue *for* the testbed's version: a criterion demoted to a one-time observation is exactly the "verified once, trusted forever" shape the template distrusts everywhere else. See transfer T1.

### 2.2 Durable dependency register (testingbed `docs/DEPENDENCIES.md`, `CONVENTIONS.md` §Dependency policy)

- **Failure prevented:** dependency creep with no auditable justification — six months later, nobody can say why a package is there, whether it was vetted, or what its license/maintenance state was at adoption.
- **Template equivalent, searched:** detection is present and stronger than the testbed's — `plan-metrics.sh` diffs the *declared* dependency list at base vs. head, covering `[project].dependencies`, dev groups, and every optional-dependencies extra (its comment calls this "the cheapest speculative-machinery detector there is"), and the review gate treats an unapproved dependency as a rule violation (`review-prompt.md` criterion 4). But the **approval and its rationale live in chat**: "No new dependencies without the owner's approval — ask first, in chat" (`template/AGENTS.md.jinja:212-213`).
- **Verdict: genuine advantage.** The template violates its own recorded maxim here — "chat is not storage" (`template/AGENTS.md.jinja:251-259`; `docs/projects/find_best_mobo/DECISIONS.md:157-159` states it verbatim as a learned lesson). A dependency approval is precisely a ruling a future session needs, and the template's own `docs/DECISIONS.md` is where rulings go; the dependency rule predates that insight and was never reconciled with it. The testbed's per-dependency entry (purpose, why-not-stdlib, license, health) is the durable artifact the template's philosophy demands but its mechanism doesn't produce. See transfer T2.

### 2.3 Deterministic protected-path check in CI (testingbed `scripts/check_protected_paths.sh`)

- **Failure prevented:** an agent's PR touching gate-defining paths merging without human sign-off.
- **Template equivalent, searched:** two layers. Binding: CODEOWNERS + the ruleset's "require review from Code Owners" (`template/.github/CODEOWNERS.jinja`; `README.md:361-375`) — deterministic, platform-enforced. Semantic: the review gate BLOCKs on gate tampering, including tampering a path-list can't see, like raising `EXEMPT_MAX_ADDED` (`review-prompt.md` criterion 5; `plan-resolve.sh:160` names it "gate tampering" in its own error text).
- **Verdict: mostly prevented by stronger means; a narrow residual advantage.** The residual: GitHub **silently ignores** CODEOWNERS entries that don't resolve — the template's own `copier.yml:98-102` warns that this "disables the gate silently rather than erroring," and its validator can only shape-check the handle. If the CODEOWNERS binding is silently dead, the deterministic layer is gone; a gate-path PR then needs only green checks, auto-merge arms, and the last line of defense is the LLM reviewer — fail-closed, but a judgment gate. `unattended-ready.sh` refuses unattended runs when the `codeowners/errors` API reports problems, which covers the driver path but not attended PRs. A dumb in-repo path check (the testbed's is ~40 lines) fails red on that day regardless of platform state, and costs one CI step. Low-severity, low-cost: transfer T3.

### 2.4 Test-evasion grep (testingbed `scripts/check_no_test_evasion.sh`)

- **Failure prevented:** acceptance tests skipped/quarantined/`.only`'d to reach green.
- **Template equivalent, searched:** `test-the-tests` catches the harmful core case *semantically* — skip the new tests and the reverted suite passes, so the check fails. `blind-tests.sh` makes any post-blind edit visible with the editing commit named; the review prompt makes weakening-to-pass a blocking finding (`review-prompt.md:95-115`).
- **Verdict: no advantage.** The template prevents this failure by stronger means. Worse, the testbed's syntactic grep would *conflict* with the template's legitimate-skip rule ("a test that needs an unavailable optional resource skips with a clear reason rather than failing," `template/AGENTS.md.jinja:142-144`). Do not transfer (see §6).

### 2.5 Three-link traceability chain with report accounting (testingbed `scripts/check_traceability.py`)

- **Failure prevented:** completion-by-scope-narrowing — a requirement silently dropped between design and "done."
- **Template equivalent, searched:** distributed across `coverage.sh` (every design `R`-id — unioned across both design documents — covered by a merged plan's `covers:`, with malformed ids a hard error because "a gate that ignores what it cannot parse fails open"), `plan-resolve.sh` (every code PR resolves to exactly one pre-landed plan), the review gate (diff judged against the plan), and `docs/acceptance.md` (every `S`-id accounted for, `pending` rows visible). The testbed's third link — "the newest report must mention every id" — has no direct counterpart, but the delivery loop *is* the accounting: `deliver-phase.sh` recomputes coverage every cycle and routes gaps back into PLAN, so an unaccounted requirement re-enters the queue mechanically instead of being caught in a report the agent writes about itself.
- **Verdict: no advantage.** Fully prevented, by means that are load-bearing (they drive the loop) rather than reportorial. The template's version is also historically hardened in exactly the spot the testbed's is naive: my parser treats any `FR-\d+` token as a requirement anywhere in the file; the template learned on a real project that ids in prose, indented schema examples, and malformed forms (`R2a`) create phantom or invisible requirements (`coverage.sh` §5-anchored extraction; `docs/escapes.md` ESC-7, ESC-19).

### 2.6 Hard size caps and anti-slop conventions (testingbed `CONVENTIONS.md`)

- **Failure prevented:** slop accumulation — oversized files, dead code, speculative abstraction.
- **Template equivalent, searched:** per-slice line **estimates as tripwires** ("a tripwire, not a target… never compress code, drop error handling, or thin tests to come in under it," `template/docs/plans/_TEMPLATE.md.jinja:86-96`) with a 3× overrun flag floored at 80 lines (`plan-metrics.sh`), reviewer criteria 8-9 (easy-to-change, legible-to-a-future-agent), vertical slicing, `docs/architecture.md` kept current per slice, and the new-dependency detector.
- **Verdict: no advantage; the template's placement is better.** A hard 400-line cap is Goodhartable in both directions (split files to duck the cap; compress to fit under it) — the exact pathology the template's tripwire language exists to prevent. The template's estimate is per-change and set by the plan the owner approved; the testbed's cap is global and set by me, speculatively.

### 2.7 Append-only assumption/question logs (testingbed `docs/ASSUMPTIONS.md`, `docs/QUESTIONS.md`)

- **Failure prevented:** silent guessing; retroactive laundering of a bad assumption.
- **Template equivalent, searched:** the plan uncertainty gate with HIGH/LOW contract test ("unsure means HIGH," `template/docs/plans/_TEMPLATE.md.jinja:23-53`), `BL-<n>` filing in `docs/BACKLOG.md`, oracle rulings as `OD-<n>` — and, unlike the testbed, the append-only property is **mechanically enforced** for the ledgers that matter (`escapes-append-only.sh`; `oracle-decisions.sh` byte-compares landed decision blocks). "Guessing is allowed; guessing silently is not" is the same doctrine as the testbed's, with enforcement.
- **Verdict: no advantage.** The testbed's append-only rule is a contract clause with no check; the template enforces the equivalent. Its version is also better integrated: assumptions attach to the plan and requirement they affect, rather than living in a parallel file.

### 2.8 The remaining testbed mechanisms

The `design-change` label (weaker authorization than code-owner review — triage-level users can apply labels), the DRAFT/ACTIVE status gate (template equivalent: `vision-complete.sh` firing at the plan boundary, plus `coverage.sh` exit 2 for a malformed/absent design), revision numbering with DROPPED markers (template: append-only ids, supersession entries, monotonic `OD` ids — enforced rather than conventional), and gitleaks (identical in both, `guardrails.yml` vs. the `secrets` job). No advantages found.

### Section 2 summary

Three genuine advantages survived the equivalence search: **continuous executable acceptance (2.1, partially), the durable dependency register (2.2), and a deterministic gate-path backstop for the silent-CODEOWNERS-unbind case (2.3)**. Everything else the template prevents by other — usually stronger, usually evidence-hardened — means. Stated in artifact terms: the testbed is a reasonable first-principles sketch of the template's CI tier, and the template is that tier plus the two tiers the testbed lacks entirely (an execution engine, and an unattended-authority model), minus the three items above.

## 3. Unjustified machinery in the template

Method: every mechanism with no testbed counterpart, justified from first principles ("what breaks without it") or flagged as candidate scar tissue. Finding up front: **remarkably little is unjustifiable**, because the repo's own discipline — every check traces to an `ESC-<n>` or a recorded ruling — means the historical justification and the first-principles one usually coincide. The honest flags are at the end.

**Justified from first principles:**

- **The oracle system** (`docs/DESIGN.oracle.md`, `oracle-decisions.sh`, `/oracle`, `OD` ids, evidence citation, vision quoting). Without it: unattended work halts at the first design-reality contradiction, or agents edit the design — the two failure modes the user's brief names (drift; blocked autonomy). The constraint set (cite only landed evidence, append-only, quote the vision sentence relied on, one tenet-violation stop) is the minimum that makes delegated design authority steerable and auditable. The R1000 offset is discussed under flags.
- **`docs/VISION.md` + `vision-complete.sh`.** Without it: an unattended judgment call has no owner-authored tiebreaker, so the oracle either stops (defeating its purpose) or invents the owner's priorities (drift at the deepest layer). The enforcement point — plans fail while it's empty, design PRs pass — is derived, not arbitrary: implementation starts at the plan (`vision-complete.sh:16-26`).
- **`owner-authored.sh`** (authorship, not approval). Without it: the owner's engagement with the design degrades to a click on a diff someone else composed, and — the script's own argument — "if any agent can land the design, there is no reason for `DESIGN.oracle.md` to exist" (`owner-authored.sh:3-20`). This is the load-bearing distinction the testbed's CODEOWNERS-only design misses.
- **The plan layer** (plans-before-code, slices, signatures, estimates; `plan-resolve/parse/lint/metrics`; the 50-line exemption cap with planning-path carve-outs). Without it: the review gate judges each diff against the *entire design* — too coarse to catch a smuggled second slice or an unjustified 4× overrun — and the owner has no pre-code approval point smaller than "the whole project." The cap without the carve-out was observed to block the design documents themselves (three owner bypasses in one session, `plan-resolve.sh:82-84,96-100`); the carve-out without the whole-diff test would be a smuggling hole (`:78-80`). Each piece has a what-breaks answer.
- **Blind test authorship + `Blind-Tests` trailers + `blind-tests.sh` + `test-the-tests`.** Without them: the agent that writes code writes the tests that judge it, and "describes what its code happens to do, bugs included, and calls that a test suite" (`template/AGENTS.md.jinja:149-155`). This replaces the testbed's human-frozen suite at near-zero human cost, which is the point of the whole exercise.
- **The escapes ledger + ratchet + `escape-refs.sh` + `escapes-append-only.sh`.** Without them: fixes without checks (the same bug repeatedly), speculative checks (slop in the gate layer), citations to entries that don't exist at judgment time (observed: one PR blocked twice, `escape-refs.sh:12-19`), and quiet rewriting of the oracle's evidence base. This is the template's answer to "which check should exist?" — demand-driven rather than speculative — and it is a *better anti-slop mechanism for the guardrails themselves* than anything in the testbed.
- **The driver layer** (`deliver-phase.sh`, `deliver-loop.sh`/`/deliver-loop`, `budget-probe.sh`, typed exit codes, hard caps). Without it: either a model babysits CI (spending budget to watch a spinner) or a human does (the exact touchpoint the system exists to remove). "The driver is a scheduler, not an agent" (`docs/automation-loop-plan.md:34`) is the correct division: deterministic control flow, model only where judgment is needed. The budget ceiling's fail-posture (probe broken → continue under PR/wall-clock caps, `budget-probe.sh:12-18`) is independently justified: never let the nice-to-have gauge become the load-bearing limit.
- **`spawn-worker.sh` isolation + role/model table + `settings.json` denies + command-line tool grants.** Without them: parallel workers collide (worktrees), a compromised or confused worker can `git push origin main`/`--no-verify` (denies + not-on-the-list grants: "not denied by a rule that a worker could argue with — they are simply not on the list," `spawn-worker.sh:136-141`), and headless workers fail silently (the `.claude/`-worktree incident: every write refused, exit 0, nothing produced — `spawn-worker.sh:38-50`). The security posture — sandbox on, scoped OAuth token not broad API keys, read-only reviewer, grants-as-arguments because fresh worktrees ignore `settings.json` — is coherent defense-in-depth, and the doctrine that grants are "the FIRST of two enforcements and not the binding one" (required checks bind every route, `orchestration.md:121-124`) is exactly right.
- **The review gate's hardening** (per-run nonce delimiters generated after the diff is read, forged-delimiter = blocking finding; `--literal-pathspecs` because plan paths are "attacker-adjacent"; IFS-not-eval; lockfile excludes; 400KB degradation to summary review; verdict on last-line-whole-match so a quoted verdict in the diff can't count). Without each: a specific prompt-injection or parser-abuse route into a fail-closed required check. This is the most security-serious file in either repo, and the testbed has nothing at this altitude.
- **`unattended-ready.sh`.** Without it: the failure class that produced most of the template's escapes — configuration living in repo *settings*, secrets, and rulesets, which no shipped file can carry ("the auto-merge workflow shipped correct three times while merged branches piled up," `unattended-ready.sh:3-17`). The testbed has the same insight as prose in its README ("two things the repo can't do for you") and no check.
- **Auto-merge + App identity + scheduled sweep.** Without them: no unattended merge at all (the testbed's model), or merges as `github-actions[bot]` whose events dispatch nothing (observed: 22 stale branches), or PAT rate-limit exhaustion overnight (observed). The identity ladder with fallbacks is justified at each rung by a named incident (`auto-merge.yml:13-46`).
- **The copier meta-layer** (`template-sync.sh` byte-for-byte replay, `update-from-template.sh`, `release-tag.yml`, `docs/projects/` evidence mirrors). This solves a *different problem* than the loop — maintaining many generated projects centrally — which is why the testbed has no counterpart. Given that goal: template-sync's tree-hash proof ("this diff is byte-for-byte what the template produces, and contains nothing else") is what makes an unplannable change safely exempt from the plan gate; release-tag exists because copier resolves tags, and an untagged merge is invisible (observed: `find_best_mobo` generated from v0.3.0 while main was ahead); the mirrors exist because cross-project evidence is how you tell a recurring gate failure from a one-off. All justified *within that goal*.
- **`docs/acceptance.md`'s agent/owner split, `architecture.md`, pre-recorded `DECISIONS.md` rulings.** Each has a one-line what-breaks: agents claiming verification they couldn't observe; future sessions re-deriving the system from code; every generated project re-asking four settled questions.

**Candidate scar tissue** (cannot be fully justified without appeal to history):

1. **The R1000 id offset** (`DESIGN.oracle.md.jinja:32-39`, enforced in `oracle-decisions.sh`). The stated justification — `R<digits>` grammar has "no namespace mechanism" — is a self-imposed constraint: a namespaced id (`OR-<n>`) would eliminate the collision by construction, and `coverage.sh` (which the template already controls) could union both grammars. The offset is the cheaper patch given that `coverage.sh`, plans' `covers:`, and the docs all already speak `R<n>` — i.e., its justification is migration cost, which is historical. Mild, contained, and honest about itself, but scar tissue by this report's definition.
2. **The dual-glossary wipe-and-sync protocol** (`README.md:424-444`: fold project words into the template's glossary, then wipe the project file, sequenced with the update that carries the words back down). The two-file split is forced by copier's replace-wholesale semantics, fine — but the wipe *sequencing* is an unenforced human-memory protocol whose failure mode (wipe before the update lands → project has no definitions in the gap) the README itself documents rather than prevents. In a repo where every other invariant of this shape got a check, this one didn't. Small stakes; still the pattern the escapes ledger would eventually catch.
3. **The SSH `insteadOf` ceremony** (`README.md:88-144`). Three interlocking constraints (CI must fetch HTTPS; the human authenticates via a host alias; copier records whatever URL was typed) resolved by per-machine global git config. Justified only by the specific environment (private template, personal account, no org secrets); it is the part of the setup most likely to break for reasons the repo can't see, and it exports fragility to every future machine. Environmental scar tissue — arguably irreducible without changing the hosting posture (public template or org account), which the README's Pro-vs-public section shows was considered.
4. **`project_name` asked-but-defaulted** (`copier.yml:12-49`). Pure workaround for copier's recorded-answers-only-if-asked behavior, and documented as such. Necessary given the tool; scar tissue by origin; harmless.

Notably **not** flagged, despite looking baroque: the 150-decision cap, the 50-line exemption cap, the 3×/80-line overrun flag, the `## Slices`-banner grammar rule, and the `--vcs-ref=HEAD` test pinning — each carries a specific incident or a first-principles failure ("a runaway loop", "a self-service bypass", "training the reviewer to ignore the signal", ESC-6, "CI validating the previous release on every PR") that survives without the history.

## 4. Placement disagreements

Concerns both repos address, located differently. Format: concern → testbed placement vs. template placement → which is correct.

**4.1 Gate-path tampering.** Testbed: agent contract + deterministic CI script + human-applied label. Template: CODEOWNERS/ruleset (platform) + LLM review criterion (semantic) + base-commit reading (a PR cannot rewrite the standard it's judged by; CODEOWNERS stops the two-PR version — `CODEOWNERS.jinja:23-28`). **Template's placement is correct, and layered better** — the platform layer is the binding one in both designs, but the template adds the semantic layer a path-list can't express (raising a cap, weakening a regex, is tampering *inside* an unprotected line). The testbed contributes one narrow patch (§2.3): a deterministic in-CI echo that survives silent CODEOWNERS unbinding. Correct answer: platform + semantic + deterministic echo — three layers, no single point.

**4.2 Definition of done.** Testbed: frozen executable acceptance tests as a required CI check. Template: per-slice blind tests in CI + prose evidence ledger at the end, honestly split agent/owner. **Split verdict, and the split itself is the lesson.** For criteria an agent can execute, the testbed's placement (CI, continuous) is correct — one observation recorded in a ledger decays; a required check cannot. For criteria needing hardware, users, or judgment, the template's placement is the only honest one — the testbed would either exclude such criteria from its acceptance suite (silently narrowing "done") or fake them. Correct answer: executable `S`-criteria live in CI; non-executable ones live in the ledger with `Verified by: owner` (transfer T1).

**4.3 Test integrity.** Testbed: syntactic (grep for skip markers) in CI. Template: structural (blind authorship — the implementation is not present to read) + semantic (`test-the-tests` — the suite must fail without the implementation) + reportorial (`blind-tests.sh`). **Template correct.** Syntax checks catch the clumsy version of the crime; the template's placement catches the crime itself, including versions with no syntactic signature (a test written weak from the start — caught by revert; a test edited to match the code — caught by trailer diff and reviewer).

**4.4 Ambiguity resolution.** Testbed: block on the human (`QUESTIONS.md`, mark BLOCKED, continue elsewhere). Template: classify by reversibility contract-test (HIGH/LOW, unsure=HIGH), attended → owner rules pre-slices; unattended → HIGH waits for an *oracle* ruling citing filed evidence, LOW proceeds on a logged default. **Template correct for its goal, with a real precondition.** Given "maximal autonomy after the design phase," block-on-human is the failure, not the safety: the testbed's placement makes the human the scheduler. The template's placement keeps work moving while keeping every guess on the record and steerable (edit the vision sentence the ruling cited). The precondition: you must actually trust the oracle's bounds — evidence citation, vision quoting, the tenet stop, append-only. The template earns that trust mechanically; absent those bounds, the testbed's placement is the safe default.

**4.5 Dependency approval.** Testbed: durable repo artifact reviewed in the PR. Template: chat approval + mechanical detection + review-gate enforcement. **Testbed correct** — the template's own "chat is not storage" doctrine decides this against its own mechanism (§2.2). Detection should stay where the template put it (mechanical, in `plan-metrics.sh`); the *ruling* belongs in the repo.

**4.6 Code-quality/scope discipline.** Testbed: global numeric caps in a conventions file. Template: per-change estimates in an owner-approved plan, flagged (never auto-blocked) at 3×, judged by a reviewer told "a slice marked OVER is a question, not a verdict." **Template correct.** The quantity being limited is deviation-from-what-was-approved, not absolute size; global caps measure the wrong thing and invite optimizing the measure.

**4.7 Environment readiness.** Testbed: README prose ("two things the repo can't do for you"). Template: `unattended-ready.sh`, a refusal at dispatch time, with a refuse-vs-note doctrine. **Template correct, unambiguously.** Same insight, one repo documents it, the other enforces it — "a warning nobody reads at 3am is decoration; a refusal at dispatch time is the same information while someone can still act on it" (`unattended-ready.sh:19-25`).

**4.8 The "is it done?" claim.** Testbed: the agent's self-authored report (traceability matrix, CI-checked for completeness of mention — but the *status column* is self-asserted). Template: mechanical coverage (`coverage.sh` drives the loop), acceptance evidence with owner-pending rows, and a standing rule that "everything merged is a statement about the queue, not about the product" (`AGENTS.md.jinja:240-249`). **Template correct.** The testbed lets the agent narrate its own doneness and checks only that the narration is complete; the template computes what it can and forces the rest to be labeled `pending` on the owner.

## 5. Autonomy ceiling

Honest touchpoint counts per design-doc-to-merged-code loop, implicit ones included. "Touchpoint" = anything requiring a human decision, unblock, or judgment call.

### Testbed

One-time setup: enable branch protection + required checks, create the `design-change` label (2, small).

Per design revision (one loop = one agent PR, by construction — `AGENTS.md` §Workflow):
1. Write/revise `design/DESIGN.md`, bump revision (the loop's input — counted for symmetry with the template).
2. Review and merge the acceptance-suite update PR for that revision (with label). *Every revision.*
3. Answer `QUESTIONS.md` blockers mid-run (0–n; each HIGH-ambiguity stops the affected requirement until answered — the human is the only unblocking authority).
4. Review and merge the build PR. *Every iteration — nothing merges without a human click, ever.*
5. Implicit: launch the agent each iteration; watch/respond to CI failures on the PR (no driver exists — the "loop" is the human re-invoking the agent).

**Honest number: 4 + n per iteration, with the structural ceiling that human-merges-everything and human-schedules-everything.** The testbed *is* the "check in when done" loop the user asked for, at the granularity of one PR — but it achieves autonomy only within a single agent run, and a multi-feature project is that cost times the number of PRs. Its aspirational number (design, then one check-in) is real only when the whole project fits one PR and zero questions arise.

### Template

One-time setup: the README ceremony — Pro-vs-public decision, SSH alias + insteadOf, `gh` auth, `claude setup-token`, minting `TEMPLATE_TOKEN` (+ optional App/`AUTO_MERGE_TOKEN`), `setup-github.sh` run, throwaway PR, ruleset verification (≈8–10 distinct human actions, several security-mandatory by design — `README.md:226-233`). Recurring maintenance: token expiry ("template updates start failing in every project simultaneously," `README.md:622-626`), and the CODEOWNERS self-approval deadlock on every gate change and every template update (admin bypass or ruleset toggle — `README.md:383-400`, `update-from-template.sh:203-207`). These amortize across loops but are real and the template is honest about them.

Per design revision, unattended happy path (`auto_merge: true`):
1. `/design` interview participation + edit (substantial — an interactive session, not a click; but it *is* the design phase both repos charge for).
2. Open and merge the design/vision PR personally (`owner-authored.sh` — deliberately irreducible).
3. Start the driver (one command).
4. End: review the result; fill/confirm `Verified by: owner` acceptance rows.

Mid-run, zero *by design*: plan rulings go to the oracle (HIGH blocks on the oracle, not the owner), unattended plans land on the un-owned `docs/plans/oracle/` path, merges are check-triggered. Mid-run, nonzero *in practice*:
5. Driver exit 4 — a green PR only the owner can merge (any CODEOWNERS-gated change, incl. template updates) — occasional, mechanical.
6. Driver exits 2/3/5/6 — readiness failure, 3-strike pattern, iteration/budget caps — each requires a human restart decision. The caps are deliberate ("stops say why"), so some number of these per long run is intended, not incidental.
7. Attended mode (`auto_merge: false` or `/deliver` alternating): add per-feature plan approval and per-PR merges — by choice, this mode reconverges toward the testbed's count.

**Honest number: ~4 per design revision plus occasional cap/ownership unblocks — but the denominator is different: one revision spans many features and many PRs, each merging with zero touches.** Per merged PR, the testbed is ≥1 human action; the template's happy path is 0. That is the actual ceiling difference, and it is architectural, not incremental: the testbed has no driver, no unattended merge, and no mid-run authority, so its ceiling cannot be raised by tuning.

**One honesty adjustment against the template:** its 0-per-PR figure currently rests on five behaviors the repo itself marks unverified-live (App-token branch deletion, pre-registration ruleset creation, the budget probe, one live smoke of the driver's session commands, one watched `/deliver-loop` web run — `docs/automation-loop-plan.md:9-15`). Until those are observed, the real number includes the debugging touches the first live runs will surface — a cost its own history (`unattended-operation.md:176-179`: every prior fault "was found by using the thing… and each was found by the owner") predicts candidly.

## 6. Transfer list

Ranked by (failure prevented) / (machinery added). All targets are the template; testbed line numbers refer to `grimsverk/testingbed@claude/agent-design-doc-template-lnr7jl`.

**T1 — Executable acceptance criteria for the agent-verifiable subset.** *(rank 1: prevents silent regression of "done"; machinery ≈ one directory + one CI job + ~20 lines in two docs)*
The change: alongside `docs/acceptance.md`, an `acceptance/` test directory for `S`-criteria an agent can execute (the ledger's own `Verified by: agent` rows are the candidate list — each already cites a command). Run it in the delivery loop's ACCEPTANCE phase *and* as a CI job; keep the path CODEOWNERS-owned like `docs/acceptance.md` already is, so criteria changes get the owner's eyes. Costs: a new place tests live; the owner reviews acceptance-test changes (bounded: only when §13 changes, which is a design edit and already owner-landed); slower CI if criteria are end-to-end (mitigable: run in the loop + nightly rather than per-PR). Buys: a criterion observed once becomes a criterion observed continuously — closing the one gap between the template's "observed, not inferred" doctrine and its acceptance mechanism (§2.1, §4.2). Fits the ratchet rule half-way: this is admittedly a speculative check by the template's standards; the honest version is to hold T1 until the first regression-after-acceptance escape, then build it — but the testbed's contribution is having the design ready.

**T2 — Dependency rulings as repo artifacts.** *(rank 2: prevents unrecoverable approval context; machinery ≈ one AGENTS.md sentence + one review-prompt clause)*
The change: replace "ask first, in chat" (`AGENTS.md.jinja:212-213`) with "ask first; the approval lands as a `docs/DECISIONS.md` entry (or a `BL-<n>` the PR cites) recording purpose, why-not-stdlib, and license, before the dependency merges." Reuse the template's existing ledgers — do not add the testbed's separate `DEPENDENCIES.md` file; the template already has the right homes and an id discipline. Costs: one more entry per new dependency (rare by policy). Buys: the template stops violating its own "chat is not storage" ruling at the exact point where future maintainers most need the record; `plan-metrics.sh` already detects the addition mechanically, so the reviewer can check entry-exists against dep-added with no new script.

**T3 — Deterministic gate-path check as a CI step.** *(rank 3: prevents a narrow but total failure — silent CODEOWNERS unbind + LLM miss + auto-merge; machinery ≈ one ~40-line script in the existing `plan` job)*
The change: a path-diff check (testbed `scripts/check_protected_paths.sh` is the shape) failing any PR that touches the CODEOWNERS-listed gate paths, with the same carve-out logic `plan-resolve.sh` already implements for planning paths; template updates pass via the existing `template/`-branch exemption + `template-sync` proof. Costs: one more step; a duplicate signal on the common path (CODEOWNERS already blocks). Buys: the deterministic layer survives the one condition that silently kills it today — an unresolvable CODEOWNERS handle (`copier.yml:98-102` documents the risk; `unattended-ready.sh` covers only the driver path). Cheap insurance, in the template's own fail-closed idiom.

**T4 — Per-requirement "why not built" accounting at stop time.** *(rank 4, marginal)*
The testbed's report rule — every id accounted as DONE/PARTIAL/BLOCKED with a citation — has one sliver the template's loop doesn't surface: when the driver stops (exit 3/4/5/6), the gap between `coverage.sh`'s output and *why each gap exists* lives in run logs. A stop-report template (`.claude/deliver-loop/run.md` already exists as the morning-read artifact) that lists uncovered ids with their blocking `BL`/`ESC`/exit-reason would make the morning read requirement-shaped. Machinery: formatting in an existing artifact. Buys: less archaeology per stop. Honest note: this is a convenience, not a failure-prevention; ranked accordingly.

### Do not transfer

- **The skip-pattern grep** (`scripts/check_no_test_evasion.sh`). Conflicts with the template's legitimate skip-with-reason rule (`AGENTS.md.jinja:142-144`); the harmful case is already caught semantically by `test-the-tests` and reportorially by `blind-tests.sh`. Adding it would generate false positives that train people to ignore red — the template's stated reason for its shellcheck severity threshold applies verbatim.
- **Hard file/function size caps** (`CONVENTIONS.md`). Directly contradicts the tripwire-not-target doctrine; the estimate+3×-flag+reviewer chain measures deviation from an approved plan, which is the right quantity (§4.6).
- **The per-iteration self-authored build report as a gate input.** The template deliberately splits this into computed facts (`plan-metrics.sh`, `blind-tests.sh` — always exit 0, feed the judge) and judged verdicts; a self-narrated status matrix would re-blend them and put the agent's claims back on the evidence side of the line the template is strict about.
- **The `design-change` label.** Strictly weaker authorization than code-owner review + owner authorship; the template's admin-bypass/ruleset-toggle answer to the same deadlock is uglier but honest about who is exercising the bypass.
- **`ASSUMPTIONS.md`/`QUESTIONS.md` as standalone files.** The template files the same content where it binds: uncertainties in the plan (with rulings recorded in place), objections in `BACKLOG.md`, escapes in the ledger. Parallel free-text logs would be the un-id'd, un-cited version of mechanisms the template deliberately made rigid — its `escape-refs.sh` header explains exactly why prose records were rejected.
- **The blanket rebuild-over-patch directive** (`AGENTS.md` §revision change). In the template, change-shape is governed by plans and slices; a standing "prefer deleting and rebuilding a module" rule would fight the plan gate (a rebuild is precisely what needs a plan) and the estimate discipline. The template's escape-driven version — rebuild when the evidence says the shape is wrong, via an oracle decision and a steward plan — is the bounded form of the same instinct.

## Closing note on the comparison's own limits

Two things this report cannot establish from the artifacts: whether the template's five unverified-live behaviors work (its own position is that nothing counts until "a branch has been seen to vanish"), and whether the oracle's bounds hold against a determined-degenerate model rather than the cooperative-but-fallible one its incident history reflects. Both are observation questions, and the template's closing commit message — "the plan is implemented; what remains is observation" — is the correct epistemic state for both. The testbed has the mirror-image limit: nearly everything in it is unobserved by construction, and its three surviving contributions (T1–T3) should be read as *designs validated by the template's own doctrine*, not by evidence of their own.
