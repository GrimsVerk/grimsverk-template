## What problem the template appears to solve

This is a Copier template that *generates* project repositories (README.md:3-5,
copier.yml:5 `_subdirectory: template`). Each generated repo is a machine for
one person ("the owner", default @GrimsVerk, copier.yml:94-97) to turn an idea
into working software with coding agents doing essentially all implementation,
while the owner's authority is preserved through mechanical gates rather than
supervision. The problem being solved, visible from the artifacts alone:

1. Owner writes intent (docs/DESIGN.md via a /design interview; docs/VISION.md
   as tiebreaker values).
2. Agents plan (docs/plans/<slug>.md, vertical slices), build (orchestrator +
   per-slice coder/test-writer pairs in worktrees), and open PRs.
3. Merging is *mechanical*: required checks green → GitHub native auto-merge.
   "The pipeline merges, not you and not the owner" (AGENTS.md.jinja:10-11).
   No agent and (under auto_merge=true) no human presses merge.
4. When reality contradicts the design mid-run and nobody is awake, an "oracle"
   role appends evidence-cited decisions to a second, un-owned design document
   (docs/DESIGN.oracle.md) so work doesn't queue on the owner overnight.
5. Every defect that reaches the owner must produce a permanent check (the
   "ratchet", AGENTS.md.jinja §Enforcement; docs/escapes.md ledger with ESC-n
   ids resolved by CI).

So: same problem as stated in the user's brief, but tuned hard for *unattended
overnight operation* — the distinguishing obsession is "what stops work when
the human is asleep, and how do we remove that stop without giving agents
authority over intent."

## The workflow it assumes

idea → /design interview → DESIGN.md (agent-written, owner-LANDED — the
owner-authored check requires the owner to open that PR) → VISION.md (must be
complete before the first plan lands; vision-complete.sh) → /plan →
docs/plans/<slug>.md on its own PR, merged BEFORE code (plan check fails a PR
whose plan isn't at its base commit) → /orchestrate builds one feature: one
branch, per-slice coder + blind test-writer in separate worktrees, Blind-Tests
trailers, assembly, one PR → required checks (CI, plan, test-the-tests, review
LLM gate, secrets, template-sync) → auto-merge on green → /deliver or
deliver-loop.sh drives the whole loop unattended, one PR in flight at a time →
acceptance pass fills docs/acceptance.md per S-id with agent/owner split →
"done" = every R-id covered by a merged plan AND every S-id evidenced.

The repo is generated by copier, wired to GitHub by scripts/setup-github.sh
(ruleset "grimsverk-gates", CODEOWNERS, secrets), and updated centrally via
copier update on template/ branches verified byte-for-byte by template-sync.

## What it expects of the human

Explicit surface (README.md "the owner's three jobs"): land vision + design;
optionally steer mid-run by editing those two documents; review/accept at the
end. Plus the setup ceremony: GitHub Pro or public repo, SSH alias, PAT minting
(TEMPLATE_TOKEN, optional AUTO_MERGE_TOKEN), claude setup-token, ruleset
configuration, throwaway PR to register checks, and the CODEOWNERS
self-approval deadlock (admin bypass or ruleset toggle) whenever gate paths
change. The owner is also assumed to be a *learner* — GLOSSARY.md's two word
lists and communication rules assume someone acquiring engineering vocabulary,
who replies while reading, and who wants dense working commentary but
high-level summaries.

## Legibility verdict

The template is highly legible as a spec — unusually so. Nearly every mechanism
carries its own rationale and often the incident that produced it (e.g. the
"22 stale branches" story in README.md:305-311, the R2a/R2b id-grammar rejection
in DESIGN.md.jinja:44-49, the relitigation-block on escape-entry ordering in
AGENTS.md.jinja:403-418). Reconstruction required no guessing about intent —
only about runtime behavior of scripts not yet read at this point.
